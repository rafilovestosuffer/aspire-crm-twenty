Part 1Why the system is shaped this way

You are about to provision 31 custom objects. Somebody chose those 31, and not 20 or 60. This part explains how, because the same method is how you will decide what your version needs — and because a data model you do not understand is one you cannot safely change.

If you only want to build, skip to Part 2 and come back. Nothing here is a prerequisite. But the single most common way a migration like this fails is that somebody rebuilt what they assumed was in use, went live, and discovered in week three that a form nobody had inventoried was still feeding leads somewhere.

1.1 The problem this method solves

A marketing-and-CRM platform accumulates configuration the way a house accumulates cables. After a few years there are forms nobody submits, workflows that were drafted and never switched on, tags that encode a process somebody left, and automations that quietly do something important four times a year.

When you replace that platform you have to answer one question, for every feature it offers:

Do we actually use this — and if we do, what replaces it?

There are two wrong ways to answer. Rebuilding everything wastes months on features nobody touches. Rebuilding what you remember silently kills the ones you forgot. The method below answers it from evidence instead.

1.2 Four rules

RULE 1

Extract with tools, judge with people

The configuration is already structured data sitting behind an API. Read it with a script. Photographing screens is slow, incomplete, and gives you no way to know what you missed. Anything a script can pull, a script pulls; humans then decide what it means.

RULE 2

Discard before you map

Every feature retired is a feature nobody has to migrate, test, document or explain. Filtering by actual usage typically removes a third to a half of the surface area. Do it first, while it is cheap.

RULE 3

Evidence, or unknown — never a guess

Every "in use" answer names its source: an endpoint that returned a count, a row in an export, a dated observation in the interface. A feature nobody has checked is recorded as unknown, and unknown is a legitimate, reportable answer.

Guessing "no" is how a live automation dies at cutover, and nobody notices for three weeks. Guessing "yes" only wastes effort. The two errors are not symmetrical, so the method never guesses at all.

RULE 4

Configuration, never contacts

The audit needs structure, not people. No contact records, no message bodies, no call recordings, no form-submission payloads. Endpoints that might carry personal data have their response bodies discarded at the moment they are read — only counts and field names are written to disk.

This is a governance position and a practical one. It also means the audit can be handed to anyone without a data-protection conversation.

1.3 The six tiers

The work is ordered so that each tier is useful on its own. If the audit is cut short, whatever you finished still stands.

1.4 The instrument: a puller that cannot write

Tier 1 is a script driven by a registry file. The registry describes each endpoint — its path, how it paginates, where the array lives in the response, and one field that matters more than the rest:

ClassEffect
configStructure. Safe to write to disk in full.
volumeMay contain personal data. The body is discarded; only a count and the field names survive, and that count is the usage evidence.
agencyNeeds account-level access. Recorded as skipped, not failed, when you do not have it — those are different facts.

Four guards make the script safe to hand to anyone:

  • GET only. Any other HTTP method is refused at the transport layer, not by convention. The script cannot modify the system it is reading, even by mistake.
  • Throttled below the ceiling. 80 requests per 10 seconds against a limit of 100, with exponential backoff. Never remove the throttle to make it faster.
  • Tokens redacted. Authorization headers are stripped from every error message before anything is printed or logged.
  • Failure is data. The first run is a discovery run: it records the status and response shape of every endpoint into a coverage report and keeps going. You read that report before you trust anything in the output.
Why the coverage report comes first

An endpoint returning 401 means a permission you were not granted — a stated limitation of the audit, not a broken script. An endpoint returning 404 means it does not exist on your account tier. An endpoint returning 0 might mean the feature is unused, or it might mean you are reading the wrong field. Those are four different conclusions and only the coverage report tells them apart.

1.5 The finding that shapes the whole project

Tier 4 exists because of a single, load-bearing limitation, and every plan built on this method has to account for it:

The platform's public API exposes workflow metadata only — id, name, status, dates. It will not tell you what any workflow actually does.

There is no steps endpoint, no actions endpoint, no versions endpoint. So GET /workflows/ answers "how many automations exist and how many are switched on". It cannot answer "what do they do", which is the entire point of the exercise.

Worse, execution counts are not available either. The discard pass in Tier 3 wants to drop any workflow that has enrolled nobody in 90 days — and that number cannot be fetched. It has to come from the execution-log view in the interface, by hand.

The route that does work is to open one workflow in a browser, capture the request the interface itself makes to fetch the step tree, and replay it across the workflow list using your own session. Three consequences follow, and all three must be planned for rather than discovered mid-run:

ConstraintHow the script handles it
The session credential expires in hours, not daysCheckpoint after every workflow and resume. A restart-from-zero design loses an afternoon. Expect to re-capture the session once or twice per full run — that is normal, not a failure.
It is an internal, undocumented interface whose shape can changeStore the raw response verbatim; parse in a separate pass. Never parse at capture time.
It sits outside the read-only token's permission storyDisclose it in the writeup rather than leaving it implicit.
Watch out

This is legitimate for a one-off audit of configuration you own. It is not a basis for anything ongoing, and it should never end up in a scheduled job.

1.6 The checklist that makes sure nothing is missed

The spine of the audit is a single file listing 111 features across 23 areas — the complete surface of the platform being replaced, whether or not this particular company uses any given one. Each row carries how to detect it, where the evidence lives, and a starting hypothesis.

Rows are never deleted. A feature that turns out to be unused is marked as such, with its evidence. That is why the list can be trusted as complete: the only way for something to leave it is to be answered.

The six answers a feature can get

DispositionMeaning
TWENTYThe CRM does this natively. Configuration only, no code.
N8NThe automation engine reproduces it with no CRM involvement.
TWENTY+N8NThe record lives in the CRM; the logic runs in the automation engine. Most of the interesting ones land here.
DROPEvidence shows it is not in use. Retire it.
ESCALATENeither tool can do it. Needs a vendor and a budget decision.
UNKNOWNNot yet checked. Not a final state — the audit is finished when this count reaches zero.
Why ESCALATE must never be hidden

Some capabilities cannot be self-hosted at any price, because the obstacle is regulatory rather than technical. Sending SMS requires a licensed carrier relationship. Phone numbers, voice menus and call recording require the same. Business messaging on the large chat platforms is only issued through approved providers. No amount of engineering changes this, for the same reason software cannot make itself a phone company.

A short, specific ESCALATE list beside a long TWENTY/N8N list is what makes the rest of the report credible. A report with no escalations is one nobody should believe.

1.7 What the evidence produced here

Run against a real account, this method turned 111 catalogued features into a decision for every one. The resulting split — reproduced from the audit file itself, not retyped — is:

DispositionCountWhat it meant in practice
ESCALATE52Mostly telephony and hosting. Consolidates into a small number of real decisions, most of which stayed deferred because the usage evidence was near zero.
TWENTY+N8N20The core of the build: record in the CRM, logic in the automation engine.
TWENTY15Native. Configuration only.
N8N14Forms, tracked links, scheduled sweeps, notifications.
UNKNOWN7Evidence rows resolved by the pull rather than by design work.
DROP3Verified unused.

Two findings from the live pull did more to shape the object model than anything else:

The account was a training business wearing a CRM

The live configuration described a funnel — a webinar, a nurture sequence, a trainer meeting, a bootcamp enrolment paid through an external link, then a cohort — flattened into contact fields and deal stages. There were three separate pipelines with 11, 8 and 4 stages, none of which mapped onto the CRM's defaults. There were 53 custom fields, every one of them on the contact record, because a contact field was the only place to put anything.

That is why the object model has trainingProgram, cohort, enrollment, webinarEvent and webinarRegistration as real objects. "Who paid for the January bootcamp and who is still sitting on a payment link" becomes a saved view rather than a spreadsheet export.

The automation history did not exist anywhere

The single hardest part of the audit was that the old platform would not say what its own automations had done. That gap is why every workflow in this build writes an automationRun record back into the CRM — every run, success and failure, queryable in one call. It costs one extra step per workflow, and it means the next person to audit this system does in an afternoon what took weeks here.

Do not

If you are running this method against a real account you intend to close: export the suppression list first — everyone who has unsubscribed, bounced or complained. That list is usually not recoverable once the account is terminated, and mailing someone who opted out is a compliance incident. Part 6 covers importing it. Do it before any termination date is agreed, not after.

1.8 Applying this to your own account

If you are adapting this build rather than reproducing it, the method transfers directly:

  1. Create a read-only token. Grant every permission ending in "readonly"; grant nothing implying write. Record the granted list — it is a stated limitation of your report.
  2. Write down the version header. Most platform APIs require one, and omitting it produces an error that reads exactly like an authentication failure and will cost you an afternoon.
  3. Verify one endpoint by hand with curl before running any script. If that returns your account object, authentication works and everything after is logic.
  4. Do a discovery run across your whole endpoint registry, then read the coverage report before drawing a single conclusion.
  5. Check five classifications by hand. If all five are right, trust the rest. If any is wrong, fix the rule and re-run everything.
Watch out

Two traps that cost real time here. A response of HTTP 200 with an empty list is the most dangerous result in an audit — it looks like "this feature is unused" and it is often "you read the wrong field name". Check the field the array actually lives under against a real response before believing any count of zero. And choose your evidence window deliberately: a 90-day window makes anything annual — renewals, compliance reviews, yearly training resets — look completely dead.
