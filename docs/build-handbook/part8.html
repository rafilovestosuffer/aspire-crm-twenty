Appendix E · How this system fails silently

Every entry below is a real defect that reached a running system. None of them crashed. Each returned success and the wrong answer, which is why they survived long enough to be expensive.

If you read one page of this handbook twice, make it this one.

Queries the API accepted and ignored

The mistakeWhat it looked likeWhat it actually did
Bracket-style filter syntaxHTTP 200, records returnedFilter ignored; whole table returned. The workflow used row zero and emailed a lead acknowledgement to an unrelated contact. Noticed only because the name in the email was wrong
Camel-case sort parameterHTTP 200, sorted-looking dataSort silently ignored. Arbitrary order, forever
Requesting 500 rowsHTTP 200, 200 rowsCapped at 200 with no warning. Every scheduled scan would have processed the first 200 rows of a growing table and reported success
Un-encoded value in a filterHTTP 400 — but only for some inputsBroke the error handler's own duplicate check on a workflow name containing brackets. The failure was logged, the handler then errored, and the alert was never sent
Timestamp with an offset instead of ZHTTP 400Fine while the timezone is UTC. The day somebody sets a local timezone, every timestamped write fails at once on a system that passed every test

Things that looked deployed and were not connected

The mistakeWhat it looked likeWhat it actually did
Error workflow bound by nameEvery workflow shows error handling configuredReferences resolve by id. None of it fires. Every failure passes silently
Workflow deployed but not activatedPresent in the list, looks correctNever runs
Form fields posted under their labelsHTTP 200Every value silently null. Inputs post by position, not by label
Testing failure handling by handThe step fails in the editor as expectedThe error workflow only fires for production executions. A manual test proves nothing
Asserting on a webhook's status codeHTTP 200A webhook answers on receipt, before the workflow runs. The 200 says nothing about the outcome

Green tests over broken code

The defectWhy every check passed
Nurture sequence referenced templates that did not existOn a fresh database no lead is old enough to be nudged, so the send path never executed
Health check read only the latest 20 runsOn a quiet system the scheduled jobs were in that page. On a busy one they are not — it then reports a dead worker on a healthy one, or misses a real failure
Consent checkbox compared to boolean trueThe test posted the field directly, where the comparison holds. A browser posts a ticked checkbox as a JSON array. Every real human who ticked the box was recorded as pending, the acknowledgement was refused, and the refusal looked exactly like correct consent enforcement
The pattern behind all three

Each was volume-dependent or client-dependent: correct on a small dataset or a synthetic client, broken with real data or a real browser. When you add a check, ask two questions — what data would have to exist for this code to run at all, and does my test speak the same wire format as the real client?

Infrastructure that fails without saying so

The failureHow it presents
The worker container is deadThe interface is perfectly healthy. Scheduled work and mailbox sync stop, silently, indefinitely
The server cannot reach its own public URLEvery metadata request answers HTTP 500 with an empty body and no log line, while the ordinary API works perfectly. Looks exactly like a bad API key
The proxy allowlist is wrongThe site looks equally healthy whether the rule works or not. Reading the file does not prove it — the proxy applies directives in its own order
The alert URL points at an undeployed workflowEvery alert posts into a 404, inside the error handler. Weeks of apparent health while nothing that broke is reported
Health check targets a hostname, not the loopback addressThe container listens on IPv4 only; the hostname resolves to IPv6 first. The check fails forever while the service is fine
Backups run and are never restoredA restore that produces an empty schema exits zero. Only a row-count comparison catches it

Appendix G · Verified API behaviour

Behaviour established by running against live instances, not read from documentation. Where the two disagreed, this is what the software actually did.

The CRM's REST API

BehaviourConsequence
Filters use ?filter=field[op]:value; comma means ANDAny other shape is ignored, not rejected
Sorting is ?order_by=field[DescNullsLast]A camel-case parameter name is silently ignored
A relation person is filtered as personIdFiltering on the relation name does not work
200 rows is a hard ceilingAsking for more returns 200, HTTP 200, no warning. Page with a cursor and compare against the reported total
Timestamps must be UTC with ZAn offset is a 400 — in filters and in write bodies
Pages do not overlap and sum exactly to the totalVerified live. Paging is safe to trust once implemented
Metadata endpoints reject every query stringAnd embed only a slice of each object's fields — merge with a real row to get the full picture
Metadata is not served in-processThe server calls its own public URL. If it cannot reach or trust that URL: HTTP 500, empty body, no log line, while the ordinary API works. §5.9
Rich-text fields take a structured object, not a stringA bare string is a 400
Default opportunity stages have no "won" stageAny pipeline mapping has to be explicit

The automation engine

BehaviourConsequence
An expression ends at the first closing brace pairA nested object literal closes it early; the rest is a syntax error
A JSON body parameter is only evaluated when the whole parameter is an expressionPartial interpolation silently sends the literal text
Sub-workflow and error-workflow references resolve by idBound by name they dangle silently. Bind ids at deploy time
Form inputs post as field-0, field-1… by positionPosting under labels returns 200 with null values
A ticked checkbox posts as a JSON array, not a booleanComparing to boolean true fails for every browser submission while passing every synthetic test
The form path lives in different places across versionsSet both, or the URL falls back to a random identifier
The error workflow fires only for production executionsManual runs never trigger it. Test failure handling through a webhook
A webhook responds on receiptThe status code says nothing about the outcome. Assert on the record
Code steps run sandboxedEnvironment access is through the engine's own accessor
The container listens on IPv4 onlyHealth checks must target the loopback address, not the hostname

The platform being replaced

BehaviourConsequence
Workflow internals are not on any public endpointThe API says how many automations exist and whether they are on. It cannot say what they do. This shapes the entire migration — §1.5
Execution counts are not available eitherThe discard pass depends on a number the API will not give you
A version header is mandatoryOmitting it produces an error that reads exactly like an authentication failure
Some list endpoints return the array under an unexpected keyRead the wrong key and you get HTTP 200 and an empty list — indistinguishable from "this feature is unused". The worst failure mode in an audit
Some endpoints require an undocumented parameterOmitted, they 422
Page-size limits vary by endpointOne endpoint's valid limit is another's 422
A default scripting user-agent may be blocked upstreamReads as an authentication failure and is not. Send a user-agent

The habit worth taking from this appendix

Verify empirically before writing logic against it. Documentation and live behaviour disagree often enough that a script written blind fails in ten places at once. Make the first run of anything a discovery run that records what each call actually returned, and read that before trusting the output.
