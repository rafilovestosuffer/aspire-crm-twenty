Part 0Orientation

Read this part once. It is nine pages, it has no commands in it, and it is the difference between following a build and understanding one.

0.1 What you are about to build

You are going to build a customer relationship management system that runs on hardware you control. By the end of Part 2 — about half an hour of waiting and eleven commands — you will have, on your own machine:

A CRMCompanies, people, a sales pipeline, notes and tasks, plus 31 custom objects shaped around a training business: programs, cohorts, enrolments, webinars, consent records
An automation engine19 workflows that capture leads, score them, chase renewals, send email, and record every run they make
A public web formHosted by your own stack. Somebody fills it in; a scored, assigned, consented record appears in the CRM seconds later
A mail catcherSo the send path runs for real without any chance of a test reaching a live human being
ProofA suite of 77 checks that submits the real form, follows the real redirect, breaks something on purpose, and then asks the CRM whether the records are actually there

Then Part 5 puts the same thing on a real server, with a real domain name, a real certificate, and a firewall.

The one idea to hold on to

Twenty holds the truth. n8n does the work. The CRM is a database with a good interface — it stores what happened. The automation engine is what makes things happen: it watches for a form submission, decides what the lead is worth, writes the record, sends the acknowledgement, and files a note saying it did. Almost every question in this book resolves to "which of those two is responsible for this?"

0.2 The system in one picture

Seven programs run side by side. Each one is a container — a packaged, isolated copy of a program plus everything it needs to run. You do not install any of them; you describe them in a file and one command starts them all.

0.3 Words this book uses

If you already know these, skip to §0.4. If you do not, this table is the only vocabulary you need for the whole build.

WordWhat it actually means
ImageA frozen, downloadable copy of a program and everything it needs. postgres:16 is an image. You never edit one.
ContainerA running copy of an image. Delete it and start another; nothing is lost, provided the data lives in a volume.
VolumeA disk area that survives containers being deleted. Your database lives in one. This distinction is the whole reason it is safe to restart things.
Docker ComposeA file describing several containers and how they connect, plus the command that starts them together. infra/docker-compose.yml is that file here.
Environment variableA setting passed to a program at startup, written as NAME=value. All of them live in infra/.env. This is where every password and address is configured.
PortA numbered door on a machine. The CRM answers on port 3000, the automation engine on 5678. localhost:3000 means "this machine, door 3000".
APIA way for programs to talk to each other instead of a human clicking. Twenty has one; that is how n8n writes records into it.
API keyA long secret string that stands in for a password when a program calls an API. Treat it exactly like a password.
WebhookA URL that something else calls to notify you of an event. The opposite of polling: you are told rather than asking.
SMTPThe protocol for sending email. It needs a server that will accept mail from you — a "relay".
Cron / scheduleRun this at 06:00 every day. Several workflows here are scheduled rather than triggered.
Reverse proxyA program sitting in front of everything else, receiving all web traffic, handling the certificate, and passing requests to the right container. Caddy does this on the server.
TLS / certificateWhat makes a browser show a padlock instead of a warning. Caddy obtains one automatically and renews it without being asked.
CIDRA way of writing a range of network addresses, like 203.0.113.0/24. You need it exactly once, to say which offices may open the automation editor.
IdempotentSafe to run twice. Almost every command here is; where one is not, this book says so loudly.

0.5 How to read this book

Commands appear on a dark background and are meant to be typed exactly as shown. A line starting with $ is what you type; everything else is what the machine says back.

$ ./infra/up.sh
# lines that begin with a hash are comments, not commands

Where this book shows what a command printed, that output is real — captured from an actual run of this build, not typed out from memory. If your screen says something different, that difference is information, and §6.7 lists what the common ones mean.

Four kinds of aside appear throughout:

Why

The reason something is done this way. Skippable on a first pass; worth reading before you change anything.

Watch out

Something that commonly goes wrong here, and what it looks like when it does.

Do not

An action that loses data or breaks something irreversibly. There are only a few of these. Take them literally.

Good

What success looks like, so you know whether to continue.

0.6 The rule that governs this whole build

One idea shapes every script in this repository, and it is worth stating before you meet it in the wild:

A system that fails loudly is safer than a system that appears to work.

You will see this everywhere. The workflow that issues bootcamp payment links refuses to start if nobody has configured the prices — rather than emailing a student a link at the wrong price. The proof suite does not check that workflows exist; it makes them run and then interrogates the database. The deployment script stops at the first failed step instead of reporting success at the end.

This costs you something. You will hit errors during this build that a more forgiving system would have swallowed. Each one is a decision somebody made on purpose, and §4.7 explains which failure each guard was written to catch.

Watch out

The most expensive bugs in this system were never crashes. They were things that returned HTTP 200 and the wrong answer: a database filter that was silently ignored and returned the entire table, a page limit that quietly capped at 200 rows, a consent checkbox that was never actually read. Nothing errored. Everything looked fine. §4.6 collects all of them in one place, and it is the single most useful page in this book once you start changing things.
