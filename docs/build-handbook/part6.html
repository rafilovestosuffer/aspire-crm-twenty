Part 6Operate it

Building this takes a day. Running it takes fifteen minutes a month, provided those fifteen minutes are the right ones.

6.1 Backups, and why a backup is not a backup

The backup container dumps both databases and archives both file volumes every night into infra/backups, keeping 30 days.

An untested backup is not a backup. It is a hope.

$ python3 scripts/verify_restore.py
$ python3 scripts/verify_restore.py --database n8n

This does not just check the file exists. It takes a fresh dump, creates a scratch database, restores into it, counts every row in both and compares them exactly, then drops the scratch copy. The live databases are never touched.

Why the comparison is the point

A restore that "succeeds" and produces an empty schema is the failure worth catching, and a bare exit code will not catch it. The row count is what turns "the command did not error" into "the data came back".

The date of the last success is recorded to a file, so it is a fact on disk rather than a memory. Re-run it monthly.

Get the backups off the machine

That directory is on the same disk as the database, which means it is not a backup — it is a second copy of a file that dies with the same disk.

$ ./infra/backup-offsite.sh user@backup-host:/srv/aspire-crm/

Schedule it nightly.

Attachments are not in the database

Files people attach to records live in a volume, not in PostgreSQL. A database-only restore gives you records pointing at attachments that no longer exist. The nightly job archives both volumes for exactly this reason — do not simplify it to a database dump.

6.2 The watchdog

A dead worker is silent. The interface stays healthy, and scheduled work simply stops.

$ sudo crontab -e
# 0 * * * * /path/to/aspire-crm-twenty/infra/watchdog.sh

Hourly, it runs the same layer verification you ran during the build and posts to the alert webhook if anything is down. Without it, the first person to notice a dead worker is whoever eventually asks why no renewal reminders went out.

Two different alerting paths

PathCovers
The watchdogThe stack — a container down, a database unreachable, the proxy dead
SYS Error HandlerThe workflows — any automation that threw, with the real error, deduplicated so one broken thing does not produce a hundred messages

You need both. Neither covers the other.

6.3 The morning check

SYS Daily Health Check asks, every morning, whether each scheduled job actually ran in the last 26 hours — querying each one by name, for the reason in §4.4.

It does not check backup freshness. That is the restore verification in §6.1, and it is the one thing on this page that has to be a human habit rather than a scheduled job.

6.4 Upgrades

Both image versions are pinned in the configuration file, and they must stay pinned.

Never run latest in production

It means the server pulls whatever was released that morning — a version nobody has run these workflows against, which can run database migrations you did not choose, at a time you did not choose. The automation engine changes node behaviour between releases, and a workflow built for one version can behave differently on the next without erroring.

To upgrade, deliberately:

  1. Read the release notes for everything between your version and the new one
  2. Verify a restore first — §6.1. This is the moment you actually need it
  3. Change the pinned version
  4. docker compose … up -d
  5. python3 scripts/stack_verify.py
  6. python3 scripts/prove_workflows.py — the whole point of having 77 checks

6.5 Importing the suppression list

Do this before the old system is terminated. It is usually unrecoverable afterwards.

Export everyone who has unsubscribed, bounced or complained, then:

$ python3 scripts/import_consent_csv.py unsubscribed.csv --dry-run
$ python3 scripts/import_consent_csv.py unsubscribed.csv

Each address gets a person — created if missing — and an opted-out consent record on the email channel, sourced as an import. Re-running skips addresses that already carry a suppressing consent, so a second import is safe.

Reconcile the counts on both sides

Not approximately. Exactly. Emailing somebody who opted out is a compliance incident, and a count that is off by forty means forty people you are not allowed to contact are about to look contactable.

6.6 Confirming payment

The enrolment workflow creates a row as payment sent and will not promote it, because a link being emailed is not money arriving. Joining instructions only fire on paid, so a person confirms:

$ python3 scripts/mark_enrolment_paid.py --email student@example.com --yes

It refuses to run without --yes, and it sends no mail itself — the next scheduled run of the cohort workflow picks the change up and sends the joining instructions.

6.9 The two things that can actually hurt

The consent list

Unrecoverable after the old account is terminated. Export it, import it, reconcile it exactly — before any termination date is agreed, not after. §6.5.

The person who knows how this works

If exactly one person can restore this system, that is the most likely thing to hurt you, and no amount of engineering fixes it. The bar: a second named operator who has completed one task from this part unaided. Reading it does not count.

Part 7Extend it

Everything here is a file in version control. That is what makes the system extensible rather than merely configurable.

7.1 Add a field or an object

The CRM lets you add objects and fields through its settings screens. Do not. A change made in the interface exists only on that instance: it is not reviewable, not revertable, and gone the next time somebody rebuilds. Six months later nobody knows why the field is there.

1

Edit the schema

- nameSingular: enrollment
  fields:
    - {name: status, label: Status, type: SELECT, options: [...]}
    - {name: referralSource, label: Referral Source, type: TEXT}   # new
2

Preview, then apply

$ python3 scripts/twenty_provision.py --dry-run --only enrollment
$ python3 scripts/twenty_provision.py --only enrollment

Existing objects and fields are skipped, never duplicated. Only the new field is created.

3

Re-validate and re-prove

$ python3 scripts/validate_workflow_queries.py
$ python3 scripts/prove_workflows.py
Watch out

Removing a field from the schema does not remove it from the instance — the provisioner only creates. Deleting a field deletes its data, so that remains a deliberate manual act.

7.2 Add a workflow

The workflows are generated, not hand-written. Editing the JSON directly works until the next regeneration overwrites it.

1

Add a builder function

In the generator, write a function that returns the workflow, and add it to the list of builders at the bottom. Copy the closest existing one — every convention you need is already in it.

2

Reuse the patterns rather than reinventing them

NeedDo this
Send an emailCall VEND Send Email. Never talk to the mail server directly — that bypasses the consent gate
Record that it ranFinish with an automationRun write, success or failure
Handle failureSet the error workflow. The deploy script binds the id
Scan a tablePage it. Assume it will outgrow 200 rows, because it will
Interpolate into a filterURL-encode it. The generator refuses to build without this
Write a timestampConvert to UTC explicitly. The generator refuses without this too
3

Generate, validate, deploy, prove

$ python3 scripts/build_n8n_workflows.py
$ python3 scripts/validate_workflow_queries.py
$ python3 scripts/n8n_deploy.py --dev --activate
$ python3 scripts/prove_workflows.py

7.3 Add a proof check

A workflow without a check is a workflow you are trusting rather than verifying. Add a function that exercises the real path — post to the real webhook, submit the real form — waits, then asks the CRM what exists.

The two rules that make a check worth having

Use the real client's wire format. The consent bug in §4.7 hid behind a test that posted a field the way no browser posts it. If a browser sends an array, send an array.

Ask what data must exist for your check to execute at all. If the answer is "more than a fresh database has", your check will pass over broken code — which is exactly how three defects survived here.

7.4 Add a language model

This is the one extension in this book that is planned rather than built. Nothing in the running stack calls a language model today. It is described here because the shape of the integration decides how safe it is, and that decision is much cheaper to take now than to unpick later.

Three of the catalogued features are waiting on it: the conversation bot, the content assistant, and review handling. All three were classed as work for the automation engine rather than the CRM, because the CRM cannot do them — its own AI action is not available in the version this book pins.

Where it plugs in

In exactly one place: a node inside an n8n workflow, called over HTTPS like any other API. It never talks to the CRM, the database or the mail server directly. The workflow calls the model, reads the answer, and writes the result to Twenty using the same REST calls every other workflow uses — so the query validator in §4.6 still checks it and the run still lands in automationRun.

There is already a home for the output. aiConversation is provisioned and in use: AI FrontDesk Handover writes one record per conversation, with the summary, the sentiment score and whether a human was asked for. A model you add writes to the same object rather than inventing a new one.

Decide this before you write a single node

Every other component in this book runs on your machine. A hosted model does not. The moment a workflow sends a lead's enquiry, a conversation transcript or a contact's name to a model API, the text of your records is on somebody else's computer — subject to their retention policy, their jurisdiction and their breach history.

That may be perfectly acceptable. It is not acceptable by accident, and for a company that sells security advice it is a question a client will eventually ask. The alternative is a model you host yourself, which is slower and less capable and keeps every record in the building. Pick deliberately, write the decision down, and put it where the next person will find it.

The rules it inherits

A language model is not exempt from anything in §7.5. Four constraints matter more than the rest.

RuleWhy
It never sends anythingVEND Send Email stays the only path to the mail server. A model may draft; a person or the consent gate decides whether it goes. A model that can send is a model that can mail somebody who opted out.
It never writes a field a human would not checkHave it write to a draft or summary field and raise a task. A model writing straight into the record of truth means nobody can later tell which facts were observed and which were guessed.
Its runs are logged like every other runSame automationRun record, same error routing. When a model starts answering badly you want the history, and this is the one system that has it.
A failure is loudFollow §4.5: if the model is unreachable or returns something unparseable, fail and alert. Never fall through to a blank summary or a default score — a confidently wrong score is worse than no score.

What not to use it for

Not consent. Not scoring that decides whether a person is contacted. Not anything where a wrong answer is invisible. The rules engine in LEAD Form Intake is worse at nuance than a model and far better in one respect that outweighs it: you can read it, and it does the same thing twice.
