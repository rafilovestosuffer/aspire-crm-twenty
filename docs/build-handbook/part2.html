Part 2Build it on your machine

Eleven commands. About forty minutes, most of it waiting. At the end you will have the whole system running locally, with realistic data in it and a suite that has proved the automation works.

Every terminal listing in this part is real output from an actual run of this build. Where your screen differs, that difference means something — §2.14 collects the common ones.

2.1 Install the prerequisites

You need Docker with Compose v2, and Python 3.9 or newer. Pick your operating system.

Linux

$ curl -fsSL https://get.docker.com | sudo sh
$ sudo usermod -aG docker $USER
$ sudo apt install -y python3 python3-yaml curl openssl git
Watch out

After usermod you must log out and back in. The group change only applies to new sessions, and until you do, every Docker command fails with a permission error that does not mention groups.

macOS

Install Docker Desktop from docker.com, start it, and wait for the whale icon to say Running. Python 3 is already present.

Windows

Install Docker Desktop, then open Settings → Resources → WSL Integration, enable your Linux distribution, and click Apply & Restart. Then close your terminal and open a new one. Do all the work from inside WSL, not from PowerShell.

Do not

Do not run apt install docker.io inside WSL. That gives you a Docker command with no Compose plugin, which produces a confusing half-working setup. Docker Desktop's WSL integration is the supported path.

Check all three

$ docker --version
$ docker compose version      # v2 — note the SPACE, not a hyphen
$ python3 --version           # 3.9 or newer

If docker compose version fails but docker --version works, the Compose plugin is missing. On Linux: sudo apt install -y docker-compose-plugin. On Windows, that is the signature of unfinished WSL integration above.

2.2 Get the code

$ git clone https://github.com/rafilovestosuffer/aspire-crm-twenty.git
$ cd aspire-crm-twenty

Everything from here runs from that directory.

Why the repository is small

Nothing about the CRM or the automation engine is vendored here. This repository is the recipe: a description of which published images to run, a schema, a workflow library, and the scripts that assemble them. Docker runs the kitchen.

2.3 The impatient path

One command runs all eleven steps in order and stops at the first failure:

$ ./infra/rebuild.sh

If it finishes green, you are done — jump to Part 3 and go look at what you built. If it stops somewhere, find that step below; each one is a section.

The rest of this part runs the same eleven steps one at a time, which is how you should do it the first time. You learn what each piece does, and when something breaks later you will know which piece owns it.

Why every step is a gate

rebuild.sh refuses to continue past a failure rather than carrying on and reporting success at the end. The expensive defects in this system were all silent — a workflow deployed but never switched on, a database query that returned the whole table instead of one row. A green run of this script is a claim that the system works, so it fails loudly rather than overstating.

2.4 Step 1 — Start the stack

$ ./infra/up.sh

This does five things: creates infra/.env from the example if it does not exist, generates any missing secret, downloads the images, starts all seven containers, and then waits until the CRM answers a health check.

The first run downloads about 3.6 GB and the CRM builds its database schema from scratch, which takes several minutes on its own. Later runs take seconds.

What it prints

Good

Twenty healthy followed by worker running. Both lines matter, and the second one matters more than it looks — see below.

Do not lose these two keys

up.sh generates four secrets into infra/.env. Two of them are unrecoverable:

  • ENCRYPTION_KEY — lose it and every secret the CRM holds becomes permanently unreadable. Connected mailboxes, stored tokens, all of it. There is no recovery path and no support line.
  • N8N_ENCRYPTION_KEY — lose it and every stored automation credential is gone.

Copy both somewhere other than this machine, now, before you continue. A password manager is fine. The file is deliberately excluded from version control, so it will not be backed up by accident.

Why the worker gets its own line

Two containers run the same CRM image. The server serves the interface and the API. The worker runs everything on a clock: scheduled jobs and mailbox synchronisation.

The interface looks completely healthy while the worker is dead. Nothing on screen is red. Scheduled work simply stops happening, silently, and you find out weeks later. That is why the worker is checked separately here, again in step 2, and again at the end of the build.

Why the health check waits five minutes

On first boot the CRM runs its full database migration set and answers nothing meanwhile. Without a long grace period those attempts count as failures, the container is declared unhealthy, and the worker — which waits for the server to be healthy before starting — gives up and never starts at all. The server then recovers on its own and everything looks fine, except no scheduled job ever runs again. That is a real failure this configuration exists to prevent.

2.5 Step 2 — Verify every layer

$ python3 scripts/stack_verify.py

This checks each layer independently rather than inferring health from one service being up: containers, then the database, then Redis, then each application's health endpoint and API.

Good

Stack healthy. The three warnings are expected on a first run: the two API keys do not exist yet — steps 3 and 4 create them — and the first backup does not run for 24 hours.

2.6 Step 3 — Create the CRM workspace

$ python3 scripts/bootstrap_workspace.py

Normally you would create the first account by clicking through a signup form in a browser. This does the same thing over the API and writes the resulting API key straight into infra/.env.

Why this is scripted rather than clicked

A build that needs somebody to click through a signup form and copy a key by hand is a build that cannot be reproduced, cannot be tested, and cannot be handed to anyone else. Every manual step is a step that will be done differently next time. That is why there is not a single "now open your browser and…" instruction in this entire part.

2.7 Step 4 — Create the automation owner

$ python3 scripts/bootstrap_n8n.py

Same idea, same reason. The key it creates is deliberately not full admin: it can manage workflows, credentials and executions, and nothing else. The key is stored on disk and used by automation, so it gets the narrowest permission set that works.

2.8 Step 5 — Build the object model

This is the step that turns a generic CRM into yours.

$ python3 scripts/twenty_provision.py --dry-run   # preview, sends nothing
$ python3 scripts/twenty_provision.py

It reads reference/twenty_schema.yaml and creates every object, field and relation in three passes — objects first, then scalar fields, then relations, because a relation cannot be created before both of its ends exist.

Good

failed 0. The counts add up: 31 objects + 172 fields + 26 relations = 229 definitions, of which 228 were created and 1 already existed.

It is idempotent — anything already present is skipped rather than duplicated, so a run that fails halfway is fixed by running it again. Try it:

$ python3 scripts/twenty_provision.py
# created 0 · already present 229 · failed 0

Changing the model

Because the schema is a file, adding a field is an edit and a re-run rather than twenty minutes of clicking — and the change is reviewable, revertable, and identical on every machine that runs it. §7.1 walks through adding one.

Watch out — this is the step that fails on a server

If this returns HTTP 500 with an empty body on a server deployment, it is almost never an authentication problem, however much it looks like one. The CRM's metadata API is not served in-process: the server makes an HTTP call to its own public URL and hands back the result. If the server cannot reach or trust that URL, every metadata request fails with a bare 500 and no log line at all, while the ordinary API keeps working perfectly. §5.9 has the diagnosis and the fix. On a laptop this cannot happen, because the URL is localhost.

2.9 Step 6 — Seed realistic data

$ python3 scripts/seed_demo_data.py --wipe

Empty screens do not teach anything, and they do not demo. This fills every view with data shaped like a real business: companies, people, opportunities, subscriptions, compliance engagements, training accounts, phishing scores, consent records and tasks.

Two properties worth knowing. It is deterministic — a fixed seed means every rebuild produces identical records, so a demo looks the same every time you rehearse it. And it is paced to stay under the CRM's rate limit, which is why it takes about six minutes rather than thirty seconds.

Why --wipe

Without it, a second run adds another 448 records instead of reproducing the same dataset. --wipe deletes only what the seeder itself created, identified by the reserved .example.com address domain and a marker on seeded tasks. It will not touch real records. With no seeded parent found it deletes nothing at all, by design.

Do not

Never run the seeder on a production server. It is demo data, and it is indistinguishable from real data three months later when somebody is trying to work out why the pipeline totals are wrong.

2.10 Step 7 — Create the automation credentials

$ python3 scripts/n8n_credentials.py

Two credentials, both referenced by name from the workflows. On a laptop the mail credential points at the local catcher, so the entire send path — consent check, template render, log write, SMTP transaction — runs for real with no mail account and no possibility of reaching a live human.

Why credentials are never inlined into a workflow

A credential typed into a step is a credential in your version control, in every export, and in every screenshot. The store keeps them encrypted and the workflow refers to them by name. This is also why losing N8N_ENCRYPTION_KEY loses all of them.

2.11 Step 8 — Validate every API call

$ python3 scripts/validate_workflow_queries.py

Ninety-one calls, checked against the schema of the instance you just built: every field name exists, every filter uses the correct syntax, every enumerated value is one the object actually declares.

Why this step exists

The CRM does not reliably reject a malformed query. Send it the filter syntax most people reach for first and it ignores the filter and returns the entire table. The workflow then happily uses row zero. Nothing errors, nothing is logged.

In the run that caused this script to be written, a lead acknowledgement was emailed to a completely unrelated contact, and the only reason anyone noticed was that the name in the email was wrong. Every rule this script enforces is a silent-wrong-data failure that reached a live run. §4.6 lists them all.

It also runs without a stack — --offline checks against the schema file instead of a live instance, which is what the continuous-integration pipeline uses.

2.12 Step 9 — Deploy and switch on

$ python3 scripts/n8n_deploy.py --dev --activate

Order matters, and the script enforces it: SYS Error Handler and VEND Send Email go first because every other workflow refers to them.

Watch out — what --dev means

Two of the 19 workflows exist only to test the other 17. One is a probe that throws an exception on purpose; the other catches alerts so alerting can be proved without a chat account. Both are correct on a laptop and dangerous on a server, where the alert sink would swallow alerts meant for a human. The server deployment never passes --dev, and §5.8 says so again.

Why deployment is a script rather than an import

The source of truth is the JSON in version control, not whatever is currently in the automation engine's database. The script is idempotent: a workflow whose name already exists is updated, never duplicated. It also rebinds sub-workflow references to the ids in this environment — references resolve by id, not by name, and a workflow imported by hand into a fresh instance ends up pointing at nothing while looking perfectly correct.

2.13 Step 10 — Prove it actually works

This is the step that separates this build from most.

$ python3 scripts/prove_workflows.py

It does not check that workflows exist. It submits the real form, follows the real redirect, posts a real unsubscribe, breaks something on purpose, triggers every scheduled job, and then asks the CRM whether the records it was supposed to create are actually there.

2.14 Step 11 — Verify everything again

$ python3 scripts/stack_verify.py
Good

Three lines confirm the build landed: 59 objects (31 custom), 10/10 of the business-specific objects present, and 19 workflows, 19 active.

This runs last, not first, deliberately. The worker can be dead while every other check passes, and a build that ends green with no worker has no scheduled jobs and no mailbox sync. Re-checking after everything has settled catches it.

2.15 When something goes wrong

What you seeWhat it means, and what to do
docker: command not foundDocker is not installed, or on Windows the WSL integration is off. §2.1.
docker compose not recognised, but docker worksThe Compose v2 plugin is missing. On Windows this is the signature of half-finished Docker Desktop WSL integration.
permission denied on the Docker socketYou ran usermod -aG docker but did not start a new session. Log out and back in.
Daemon not reachableDocker Desktop is not running. Start it and wait for Running.
Never becomes healthyRead the log: docker compose -f infra/docker-compose.yml logs server. On a first boot, give it five minutes before concluding anything.
worker STILL not runningScheduled work will silently not happen. Usually the server took longer than the health grace period on first boot. docker compose -f infra/docker-compose.yml up -d worker.
Provisioner returns HTTP 500On a laptop, check the CRM is actually healthy. On a server, this is the self-URL problem — §5.9.
Automation API answers Cannot GET /api/v1/workflowsThe container restarted and has not finished booting. Wait ten seconds and re-run.
Enrolment check fails with HTTP 500Correct behaviour when no payment links are configured. §4.5 explains why this is a feature. Set ENROL_PAYMENT_LINKS in infra/.env, recreate the automation container, redeploy.
Everything worked yesterday, nothing works todayCheck the containers are actually up. ./infra/up.sh is safe to re-run and restarts anything stopped.

Starting over

$ ./infra/up.sh --down       # stop, keep all data
$ ./infra/up.sh              # start again
Do not, unless you mean it

./infra/up.sh --destroy deletes the databases and every workflow. It asks you to type DESTROY in full, which is the only protection you get. There is no undo.
