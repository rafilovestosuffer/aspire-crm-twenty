Part 5Build it for real: the server

The laptop stack and the server stack are the same files. What changes is one configuration file, one overlay, and a reverse proxy in front. Nothing is rebuilt and nothing is untested at cutover.

Budget half a day, most of it waiting for DNS.

5.1 What you need before you touch the server

RequirementDetail
A server4 cores, 8 GB RAM, 60 GB SSD as a minimum. 8 cores and 16 GB for real load. On 4 GB the CRM and the database contend and the interface feels slow under any load worth having.

Confirm DNS before you start

The certificate authority validates by fetching a file over HTTP from the name you claim. If DNS is not live yet the request fails, the proxy serves an untrusted certificate, and browsers refuse the site. Worse, failures are rate limited — discovering a bad DNS record during the real request costs you an hour of waiting.

$ dig +short crm.example.com
$ dig +short auto.example.com

5.2 Prepare the host

$ sudo apt update && sudo apt upgrade -y
$ sudo apt install -y ufw git python3 python3-yaml curl openssl

# The SSH rule goes FIRST, or enabling the firewall locks you out.
$ sudo ufw allow 22/tcp
$ sudo ufw allow 80/tcp
$ sudo ufw allow 443/tcp
$ sudo ufw --force enable

$ curl -fsSL https://get.docker.com | sudo sh
$ sudo usermod -aG docker $USER
$ exit                       # log out and back in, or docker stays denied

Log back in, clone, and harden:

$ git clone https://github.com/rafilovestosuffer/aspire-crm-twenty.git
$ cd aspire-crm-twenty
$ sudo ./infra/harden-host.sh    # unattended upgrades + fail2ban. Leaves SSH alone.
Watch out

Some hosting providers do not filter any traffic by default, which means ufw is your only firewall — do not skip it. Others offer a separate firewall in their control panel; if that is enabled, allow 22, 80 and 443 there too, or the certificate request times out with no explanation.

5.3 Generate the environment

$ ./infra/init-vps-env.sh --yes

This generates the four secrets (and refuses to rotate any that already have a value), sets the public hostnames and the HTTPS scheme, clears the local-only settings that must never travel from a laptop, and then lists the lines only you can fill in.

Back up two keys before going further

ENCRYPTION_KEY and N8N_ENCRYPTION_KEY, to a password manager, now. Lose the first and every secret the CRM holds becomes permanently unreadable. There is no recovery path and no support to call.

Do not copy a laptop configuration onto a server

Two settings make this actively dangerous. A laptop's mail allowlist would become the only addresses your server will ever mail. A laptop's alert URL points at a workflow that is not deployed on a server, so every alert would be posted into a 404 — inside the error handler, whose entire job is making sure a failure reaches a person. The system would run for weeks looking healthy while nothing that broke was ever reported. The preflight check fails on both.

5.4 Fill in the four things it cannot know

$ nano infra/.env

# The mail relay. A workspace relay is not the same host as a personal account.

5.6 Rehearse the certificate

Optional, and worth the ten minutes the first time. Before the real run, switch the proxy to the certificate authority's staging endpoint by uncommenting the marked line in infra/Caddyfile, then:

$ ./infra/up.sh --vps
$ docker compose -f infra/docker-compose.yml -f infra/docker-compose.vps.yml logs -f caddy

You want certificate obtained successfully. Your browser will warn that the certificate is untrusted — that is expected from a staging authority and means the challenge worked. Staging has far looser rate limits, so a misconfigured DNS record costs you nothing here.

Then comment the line out again and recreate the proxy. Real certificates arrive within a minute, and renewal is automatic — there is no cron job to add and nothing to diarise.

5.7 The single most important line in the file

The automation editor holds every credential in the stack.

The automation host has to be publicly reachable — the public form and inbound webhooks depend on it. But everything else on that host is the editor, and the editor can read every stored credential. Exposing it to the internet is the single largest avoidable risk in this deployment.

N8N_EDITOR_ALLOWED_IPS=203.0.113.0/24 198.51.100.42/32

Space separated, CIDR notation, a single address written as /32. Public forms, webhooks and the authentication callback stay open to anyone; only the editor is gated.

Both ways of getting it wrong fail safe

Leave it unset and the proxy refuses to start at all, rather than starting with the editor open. Set it wrong and you lock yourself out rather than letting the world in. Both are the safer direction, and you can still reach the proxy over SSH either way.

This is a line in the configuration file, not an edit to a tracked file, so it will not fight the next update. After changing it, recreate the proxy container.

The rules are proven, not assumed

Step 11 of the deploy runs the real proxy configuration against the running stack and checks each rule from a client outside the allowlist: the editor answers 403, while the form, the webhooks and the authentication callback go through. Then it widens the allowlist by the one line an operator is told to edit and confirms the editor is served.

This matters because the site looks equally healthy whether that rule works or not. Reading the file does not prove it either: the proxy applies directives in its own order, not the order they are written.

5.8 Deploy

$ ./infra/deploy.sh

Eleven gated steps, about fifteen minutes, stopping at the first failure. Every step is idempotent, so if it stops part-way you fix what it named and run it again.

1Start the stackWaits until the server container can fetch its own public URL — see §5.9
2Check the workerSeparately, for the reason in §2.4
3Create the workspaceWith a generated password, not the demo one
4Create the automation ownerSame password
5Build the object modelThe step that exposes the self-URL problem
6Create credentialsRefuses to invent a mail relay rather than silently sending nothing

8Deploy and activateWithout --dev

10Prove both databases restoreOn this machine's own disk
11Prove the proxy rules hold§5.7
Three things not to do here
  • Do not run the Python steps by hand. One command is the whole build, including the restore proof and the proxy proof that a hand-run list skips.
  • Do not seed demo data. It is demo data, and three months later somebody will be trying to work out why the pipeline totals are wrong.
  • Do not pass --dev. That deploys the alert sink, which swallows alerts meant for a human, and the failure probe, which throws on purpose.

5.9 When the object model step returns HTTP 500

This is the failure that wastes an evening, so it gets its own section.

It is not an authentication problem, however much it looks like one.

The CRM's metadata API is not served in-process. The server makes an HTTP call to its own configured public URL and hands back the result. If the server cannot resolve, reach, or trust that URL, every metadata request answers HTTP 500 with an empty body and no log line at all. The provisioner, the query validator and the stack check all fail together and none of them names the cause.

Meanwhile the ordinary API keeps working perfectly, which is exactly what sends people looking at the API key.

Ask the server directly

$ docker compose -f infra/docker-compose.yml -f infra/docker-compose.vps.yml \
    exec server curl -sS -o /dev/null -w '%{http_code}\n' "$SERVER_URL/healthz"
What you seeWhat it means
could not resolve hostThe container network has no alias for the public name. The overlay sets one — check it is not commented out. Without it the server only reaches its own public URL if the provider supports hairpin routing, which is not something to discover mid-deploy.
certificate verify failedUsually the certificate has not finished being issued. Until it is, the proxy answers with a self-signed one that the server does not trust. Check the proxy log, fix DNS or port 80, wait, then re-run the deploy — it is idempotent.
connection refusedThe proxy is down, or the URL names a host that is not it.
200The self-call is fine; the problem is elsewhere.
On an internal server this is guaranteed

Internally the certificate always comes from the proxy's own authority, which the application does not trust by default. The internal deployment path copies that authority's root out of the proxy container into a directory and points the application at it — the certificate store is owned by root with restrictive permissions and the application does not run as root, which is why it is copied rather than mounted.

5.12 The variant: a server with no public address

If the machine sits on an office network behind NAT, most of this part still applies — but three things change:

AspectHow it differs
CertificatesIssued by the proxy's own internal authority, not a public one. Every client machine has to be told to trust that authority's root once. §5.9 explains why the application also has to be told.
The editor allowlistNot used. The network itself is the boundary — the host is unreachable from outside the office by definition.
Public forms and webhooksDo not work from outside, because nothing outside can reach the server. If you need a public form, that traffic has to be brought in deliberately.

Preflight and deploy both take an --internal flag that skips the public-address and public-DNS checks — which a correctly configured private server is supposed to fail — and selects the internal overlay.

5.13 What this part does not do for you

  • Monitoring beyond the watchdog. Worker liveness, workflow failure rate, disk, and backup freshness. Part 6 has the pieces; something has to run them and shout.
  • A second operator. One person who can restore this system is a single point of failure, and it is the most likely thing to actually hurt. The bar to clear: somebody else has completed one task from the runbook unaided.
  • Load testing. A local build cannot tell you how the interface behaves at your real record volume.
