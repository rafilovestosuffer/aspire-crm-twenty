Part 4Understand it

Part 2 built the system. This part explains it, so that when you change something you know what you are changing — and so the traps that cost this build weeks are ones you never have to discover.

4.1 Seven containers and what each is for

ContainerImageJob, and what breaks without it

servertwentycrm/twentyThe CRM interface and its REST API. This is what you see in a browser.
workertwentycrm/twentyThe same image, run differently. Handles everything on a clock — scheduled jobs, mailbox synchronisation. The interface is perfectly healthy while this is dead.

backuppostgres:16Dumps both databases and both file volumes nightly, keeps 30 days.

Ports

Only two are published on a laptop: 3000 for the CRM and 5678 for the automation engine, plus 8025 for the mail catcher. The database and Redis are not published at all — they are reachable only from inside the Docker network, by name. On the server, even 3000 and 5678 are bound to loopback and Caddy is the only thing listening publicly.

Watch out — two different addresses for the same CRM

Inside the Docker network the CRM is http://server:3000. From your browser it is http://localhost:3000. The workflows use the first, because the second does not resolve inside a container. On a server the public address is a third thing again. Getting these confused is the most common configuration error in this build — §5.9 covers the version of it that produces a completely silent failure.

Volumes — what survives

VolumeHolds
db-dataBoth databases. The important one.
server-local-dataFiles people attach to CRM records. Not in the database. A database-only restore leaves records pointing at attachments that no longer exist, which is why the backup job archives this too.
n8n-dataThe automation engine's own files.

Deleting a container loses nothing. Deleting a volume loses everything, which is the entire difference between up.sh --down and up.sh --destroy.

31 custom objects sit alongside the CRM's own 28. They fall into four groups.

Why give a home to things the CRM cannot execute

The alternative is leaving channel data in whichever vendor sent it, which recreates the exact problem a migration is meant to solve: business truth scattered across systems that disagree. The CRM becomes the record layer for everything; execution stays wherever it has to be.

Reading the schema file

reference/twenty_schema.yaml is the source of truth. One object looks like this:

- nameSingular: enrollment
  namePlural: enrollments
  labelSingular: Enrollment
  labelPlural: Enrollments
  description: A student's place on a cohort, and whether they have paid.
  icon: IconCertificate
  fields:
    - {name: status, label: Status, type: SELECT,
       options: [ENQUIRY, PAYMENT_SENT, PAID, ATTENDED, COMPLETED, CANCELLED]}
    - {name: tier, label: Tier, type: SELECT, options: [BRONZE, SILVER, GOLD]}
    - {name: amount, label: Amount, type: CURRENCY}
  relations:
    - {to: person, label: Student, reverseLabel: Enrollments, type: MANY_TO_ONE}
    - {to: cohort, label: Cohort, reverseLabel: Enrollments, type: MANY_TO_ONE}

Options are written as plain labels; the provisioner derives the stored value, the display position and a colour. Relations are created in a third pass, after every object exists, because a relation cannot be built before both of its ends do.

4.3 Pattern one — the consent gate

This is the most important design decision in the build.

Exactly one workflow is allowed to talk to the mail server.

VEND Send Email is a sub-workflow. Every other workflow that wants to send something calls it. It does four things in order:

  1. Looks up the recipient's consent record for the email channel
  2. If the status is anything other than opted in — refuses, writes a messageLog row with the reason, and returns
  3. Otherwise renders the template and performs the SMTP transaction
  4. Writes a messageLog row recording what was sent

Because there is only one path to the mail server, the check cannot be forgotten in a new workflow. Somebody adding workflow number twenty gets consent enforcement whether they thought about it or not.

Three rules that make the record meaningful

  • It is populated before the old system is switched off. A suppression list is usually unrecoverable after account termination. Part 6 covers the import.
  • Every send path consults it. A consent record nothing checks provides no protection and considerable false assurance — worse than none at all.
  • Unsubscribes write back into it. MSG Inbound Events listens on a webhook for unsubscribe, bounce and complaint events and flips the record. Without this it drifts out of date within weeks.
A ticked box is a request, not an override

If somebody has ever opted out, bounced or complained, a new form submission does not re-subscribe them. It records PENDING, keeps the prior status as proof, and a human decides. This is deliberate: the most common way an organisation mails somebody who opted out is a re-submission silently resetting their state.

4.4 Pattern two — every run is recorded

Every workflow finishes by writing an automationRun row: which workflow, whether it succeeded, and on failure the real error message, not a generic one.

This costs one HTTP step per workflow and buys three things:

  • "Did the renewal sweep run this morning?" is a query, not an investigation
  • SYS Daily Health Check can ask, every morning, whether each of the scheduled jobs ran in the last 26 hours — by name
  • Whoever audits this system next does in an afternoon what took weeks here
Watch out — the bug this pattern caused

The health check originally read the most recent 20 runs and looked for the scheduled job names in that page. Form intake writes a run on every submission, so on a busy day the scheduled jobs fell off the page and the check reported a dead worker on a perfectly healthy one — or, worse, missed a sweep that had genuinely failed. It now queries each job by name and time window. Volume changes behaviour; §4.6.

4.5 Pattern three — refuse rather than guess

ENR Bootcamp Enrolment issues a payment link for the price tier a student chose. The links live in configuration. If a tier has no link configured, the workflow throws.

The result is an HTTP 500 on the enrolment webhook, an alert, and a FAILED run record. No enrolment happens. That looks like a bug and is the opposite of one — consider the alternatives:

If it guessedConsequence
Sent an empty linkStudent cannot pay; looks like incompetence; possibly nobody notices for days
Fell back to another tier's linkStudent is charged the wrong amount. A refund, an apology, and a reconciliation problem
Skipped the emailSilent. The worst option: revenue simply stops arriving and nothing says so

Failing loudly costs one enrolment and produces an alert naming the exact missing configuration. That is the cheapest of the four outcomes, so the workflow is written to take it.

Good

If you hit this during your build, you have not broken anything. Set ENROL_PAYMENT_LINKS in infra/.env, recreate the automation container so it picks the value up, and redeploy.

4.6 Pattern four — the queries that fail silently

This is the most useful page in this book once you start changing things.

The CRM's REST API does not reliably reject a malformed query. It accepts it, ignores the part it did not understand, and returns HTTP 200 with the wrong answer. Every row below is a real defect that reached a live run.

PurposeCorrectWrong — and what happens
Filter?filter=field[eq]:value?filter[field][eq]=value — ignored; returns the entire table. The workflow then uses row zero. This one emailed a lead acknowledgement to an unrelated contact.
Multiple?filter=a[eq]:1,b[eq]:2 (comma means AND)—
In a set?filter=status[in]:[A,B]A bare comma list is a 400
Substring?filter=domainName.primaryLinkUrl[ilike]:%acme%—
Sort?order_by=field[DescNullsLast]orderBy= — silently ignored. You get an arbitrary order and never know
Relation?filter=personId[eq]:<uuid>The relation is called person; the filter key is personId
Page size?limit=200 is the hard ceiling?limit=500 — returns 200 rows, HTTP 200, no warning
Timestamps2026-08-16T21:12:12.072ZAn offset like +00:00 is a 400, in filters and in write bodies alike

The 200-row ceiling deserves its own paragraph

Every scheduled scan in this build originally asked for 500 records. The ceiling is 200, and asking for more returns 200 with no error. With a few dozen records in the test data, nothing noticed. In production some months in, the sweep would have silently processed the first 200 rows of a larger table and reported success.

Any scan that can outgrow 200 rows must page: request a page, then follow the cursor until the response says there are no more. Compare what you hold against the reported total and fail if they differ — a sweep reporting "all clear" over the first page of a larger table is worse than one that errors.

Two more that are pure trap

Timezones. Timestamps go to the CRM as UTC with a Z, always. The obvious way to format "now" in a workflow renders in the workflow's configured timezone. That is identical to UTC while the timezone is UTC — and the moment somebody sets a local timezone, which is a reasonable thing to do, every timestamped write starts failing at once, on a system that passed every test.

Escaping. Every value interpolated into a filter must be URL-encoded. A space, bracket or colon corrupts the query into a 400. This broke the error handler's own duplicate-check on a workflow name containing brackets: the failure was logged, the handler then errored on the next step, and the alert was never sent. A safety net that fails silently on some inputs is worse than no safety net, because it is trusted.

4.7 Pattern five — three gates, and the bug each one catches

Three things stand between a change and production. Each exists because of a specific defect that got through.

GATE 1

The generator refuses to emit broken code

The 19 workflows are generated by a script, not hand-written, so they share conventions no human would maintain across nineteen files. The generator also lints what it is about to write and refuses on:

  • An expression containing a nested object literal — the syntax ends at the first closing brace pair, so {{ {"a": {"b": x}} }} terminates early and the remainder is a syntax error
  • A timestamp formatted without an explicit conversion to UTC
  • A filter value interpolated without URL-encoding
GATE 2

The validator checks every call against the live schema

All 91 API calls, against the instance you actually built: field names exist, filter syntax is the form the API honours, enumerated values are ones the object declares, no limit exceeds the ceiling. This is the gate that catches every row in §4.6.

GATE 3

The proof suite makes it run and then interrogates the database

77 checks. Not "does this workflow exist" — it submits the form, follows the redirect, posts the unsubscribe, breaks something deliberately, and then asks the CRM whether the records are there.

What a passing suite still does not prove

A check only proves the code it actually executed. Three defects passed every check before they were found, and all three were volume-dependent: correct on a small dataset, broken in production some months in.

DefectWhy the suite was green over it
The nurture sequence asked for email templates that did not existOn a fresh database no lead is old enough to be nudged, so the send path never ran. The suite went green over code that would have thrown on every send.
Every scan asked for 500 rows against a 200 ceilingWith 32 submissions in the test data, the ceiling was never reached.
The health check read the latest 20 runsOn a quiet system the scheduled jobs were in that page. On a busy one they are not.

When you add a check, ask what data would have to exist for it to execute at all.

The fourth: a green suite over a broken browser path

The consent checkbox is worth its own note, because it is the sharpest example of this whole category.

The intake workflow read the tick box by comparing it to boolean true. The proof suite posted the field directly and that comparison held, so the check passed. But a real browser posts a ticked checkbox as a JSON array of the selected option labels — the literal text [""] — which is not boolean true.

The consequence: every genuine human who ticked the box was recorded as PENDING, the acknowledgement was refused, and the refusal looked exactly like correct consent enforcement. The suite was green. The system was broken for every real user and correct for every test.

The fix, and the lesson

The workflow now accepts an array, the string, or the boolean. More importantly, the proof suite now posts the consent field byte-for-byte the way a browser posts it. Reverting the workflow fix makes the suite fail in exactly the right two places. A test that does not use the real client's wire format is testing something other than your system.

4.8 Traps in the automation engine itself

Six behaviours that are not obvious and each cost real time.

BehaviourConsequence
An expression ends at the first closing brace pairA nested object literal closes it early and the rest is a syntax error. Put a space between the braces.
Sub-workflow references and error-workflow settings resolve by id, not nameBound by name they dangle silently. Every workflow looks like it has error handling and none of it fires. This is why deployment is a script that binds ids at deploy time.
Form inputs post as field-0, field-1… by positionNot by label. Posting under the labels returns HTTP 200 with every value silently null.
The error workflow fires only for production executionsA manual run in the editor fails and the error workflow is never called. Testing failure handling by hand proves nothing — which is exactly why the failure probe is webhook-triggered.
A webhook answers on receipt, before the workflow runsHTTP 200 says nothing about the outcome. Assert on the record written, never on the status code.
Code steps run sandboxedEnvironment variables are read through the engine's own accessor, not the language's usual one.
